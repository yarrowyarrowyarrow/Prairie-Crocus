# V3.68 — Prairie Crocus

**Asked:** the owner: "I'd like to rename the app to 'Prairie Crocus'. Can you make
this change across the app and also tell me what I need to update on my end in
github to make this change. I'd like for this to go on a new branch."

The app was PermaDesign until V1.69 and Site & Pattern from V1.69 to V3.67. Its
icon has been a prairie crocus since V3.17 (`assets/icon/source_prairie_crocus.jpg`),
so the new name is the one the program already showed.

## The rule, carried from V1.69

**A rebrand renames what people see, not what an installed copy is found by**
(`.claude/skills/legacy-lessons` §13). Everything below sorts into those two.

## Renamed

- `branding.APP_NAME`, so the window title, About, the start screen, the
  feedback subject and every message built from it.
- Every literal "Site & Pattern" a person reads: dialogs (the autosave restore,
  the file pickers' "Prairie Crocus Files"), the installer's pages and its
  "still open" message, the Mac DMG's read-me and volume name, the review tools'
  headings, the 3D and map pages' titles, the CLI's description, the AI prompt.
- Comments and docstrings that name the app (same length, so no line moved).
- **The download files**: `PrairieCrocus-V3.68-Setup.exe` and
  `PrairieCrocus-V3.68.dmg`, and the release notes in both workflows. This is
  safe only because `github_releases.Release.asset_for_extensions` picks an
  asset by extension, never by name, so a copy already installed finds the new
  files. A test now says so.
- **The Mac bundle**: `Prairie Crocus.app` (Finder shows the file name, not
  `CFBundleDisplayName`). Cost: the first update from a V3.67 copy leaves the old
  `SiteAndPattern` app beside the new one, because the old copy's own
  instructions say "choose Replace" and there is nothing of that name to replace.
  From V3.68 the message adds a third step: move an old `SiteAndPattern` to the
  Bin. Both copies read the same data, so nothing is lost either way. The bundle
  identifier keeps `com.siteandpattern.app`.
- **Windows shortcuts and Settings › Apps**: the Start-menu folder, the shortcut
  and the uninstall entry's `DisplayName` say Prairie Crocus. An install (update
  mode included) deletes the old `Site & Pattern` Start-menu folder and desktop
  shortcut, and puts a desktop shortcut under the new name if there was one under
  either. A fresh install goes to `Program Files\Prairie Crocus`.
- The User-Agent (`PrairieCrocus/<version>`, the updater's, the flora reader's,
  three dev scripts'). Nothing keys on it; OpenStreetMap's and Nominatim's
  policies only ask that it name the app.
- Living docs: README (with a "formerly Site & Pattern" line), INSTALL, BUILD,
  USER_GUIDE, MAINTENANCE, AGENT_API, the design philosophy's title and its note
  on the name, CLAUDE.md, the skills.

## Kept, on purpose

| Kept | Why |
|---|---|
| Data folder `Site & Pattern` (`branding.DATA_DIR_NAME`) | It holds every design (`saves/`), the database and the downloaded packs. V1.69 moved it once, but then the designs were not in it. `migrate_legacy_into` swallows a failed move and the app makes a fresh folder, and from then on the "already migrated" guard never tries again: one file held open by an antivirus scan or a synced AppData would show a person an empty start screen, silently and for good. Nobody opens the folder by hand; the docs now say why it has the old name. A migration can be its own increment if the owner wants it. |
| `SiteAndPattern.exe` | A pinned taskbar icon points at the file, and the program's code is inside it (PyInstaller one-dir). A new name would leave the old exe beside the new one, and a pinned icon would run old code over a new `_internal`. |
| Installer `REG_KEY`, `UNINSTALL_KEY` | `InstallDirRegKey` reads `REG_KEY`, so a hand-run install finds the existing folder; one uninstall key means one entry in Settings › Apps. |
| The folder an existing copy is installed in | Update mode installs into `/D=<its own folder>`. |
| Repo slug and URLs (`yarrowyarrowyarrow/Site-and-Pattern`) | The repository has not been renamed. If it is, GitHub redirects web, git and API requests, so nothing breaks; the slug can then follow (see below). |
| `~/.site-and-pattern_autosave.perma.geojson` | Unsaved work from before the update is recovered from it. |
| `site-and-pattern auto-update` stash label | The source-checkout updater finds its stash by it. |
| `site-and-pattern-debug.log`, review pages' `localStorage` keys, `SITEANDPATTERN_ALLOW_NETWORK`, icon file names, `permadesign.*` | Diagnostics people have been asked to send, the owner's saved review progress, a documented dev switch, and the V1.69 identities. |
| The website, GrowNativePlants | Its own name (`static_site_render.SITE_NAME`). Its About page names the app through `APP_NAME`, so a rebuild says Prairie Crocus. |
| History: `docs/plans/`, the review and test write-ups, `docs/homeowner/`, the roadmaps, the letter to FNA | Records of what was true when written. |

`tests/test_app_name.py` holds both halves: no string in `src/` (outside
docstrings) carries the old name unless it is one of the identities above; the
installer keeps `APP_EXE`, `REG_KEY` and `UNINSTALL_KEY` and removes the old
shortcuts in install and uninstall; the build, spec and workflows agree on the
new file names; the updater still matches by extension. Seen failing on a
"Site & Pattern: " put back into `feedback.py`.

## On GitHub (the owner's side)

Nothing on GitHub has to change for this release to reach people. Optional:

1. The repository's About box (description, website) and topics.
2. Renaming the repository. GitHub redirects the old name for web, git and the
   API, so installed copies keep updating; the redirect breaks only if a new
   repository is ever created under the old name. Then the slug and URLs in
   `src/github_releases.py`, `src/http_utils.py`, `src/controllers/update_flow.py`,
   `src/flora_read.py`, the website's links and the docs can follow in an
   increment of their own, and each clone's remote should be updated.
3. Old release titles keep their old names; nothing reads them.

## Not verified here

- The Windows installer was compiled by its test where NSIS is installed (CI);
  no session has run update mode on a real Windows machine over a V3.67 install
  with the old shortcuts.
- The Mac bundle with a space in its name: the build script quotes `$APP`
  throughout, but only the Mac runner builds it. The V3.68 push's
  release-macos job is the check.
