# V3.69 — a new tester, and what their afternoon found

**The owner:** "I got a user to test the app. This is some of the feedback they
gave me with some additional things I added from observing their use. Please
document this feedback and explore how this shows up in the code. Come up with an
overview style plan, we will plan each individual section before we begin work on
it."

This is an **overview plan**. It records the feedback, what the code does today
for each item, and how the items group into sections (F276–F287). It does not
design any section: each one gets its own plan, on its own branch, before work
begins. Nothing in the app changes in V3.69.

The feedback itself, verbatim, is in [`USER_FEEDBACK.md`](../USER_FEEDBACK.md)
under *2026-11, a fourth tester*.

## What this round is like

Round 1 (2026-07) was mostly *reach*: working features behind a dead control.
This round is like that again, but with one difference: the simple app (V3.21)
now hides tools on purpose, and **four of the tester's complaints are tools that
exist and are hidden by the switch they could not find**: the walker's net, the
Plant tool in the walk, the year-by-year Flyover and the bee's *Tour the year*.
The other big theme is **the site scan**. The tester trusted it, and it is the
least reliable thing in the app, for a reason nobody had written down (below).

## The finding to read first

**Installed copies of the app never use the canopy-height map.** The tree scan
asks `tree_detect_chm.detect_trees_chm` first. That needs `rasterio`, and
`requirements.txt` leaves rasterio out on purpose: it broke the frozen builds
(its own comment, lines 23–29). Both release workflows install only that file.
So every installed copy falls back to `tree_detect.detect_trees`, which reads tree
crowns from the colours of the satellite photo, guesses heights from shadows or
from the crown's width, and says *"Couldn't reach the canopy-height map, so read
the satellite photo instead (less reliable)"*. That message is wrong too: nothing
failed to *reach* anything. The tester's three tree complaints are what the
fallback is expected to do: trees missed, heights off, conifer and broadleaf mixed
up.

Two more things make the conifer/broadleaf mix-up worse whichever path runs:

- `tree_detect._classify_foliage` answers only when the crown's colour is clear,
  and leaves the rest unknown (P9).
- `scene_contract.py` (the `existing_tree` branch) then draws **every unknown tree
  as a spruce**, because the shade model treats unknown foliage as year-round
  shade. That is right for shade and wrong to look at: a poplar with unknown
  foliage shows up as a conifer.

And the 3D models: an existing tree goes into the scene with `genus` set to
"spruce" or "", and with no `drawn` block. So it gets the **pre-V3.50 generic
tree**, not the crowns V3.50 builds from a species' read crown (`tree_habit.py`,
`03e-crowns.js`). The tester's "old placeholder" is exactly that.

**Not verified:** the tester ran V3.67 (the owner's second message), but not
whether it was the installer or a source checkout, nor what the scan's status line
said. If it was a source checkout with rasterio installed, the first finding does
not apply. The status line says which source the scan used.

### F276 — Existing trees you can trust (item 1)

*Today:* the finding above. Detection: `tree_detect.py` (RGB, 1,220 lines) and
`tree_detect_chm.py` (canopy-height, needs rasterio). The flow is
`tree_detect_flow.py`, the scan `features_scan_flow.py`, the review list the
scan's dialog. Drawing: `scene_contract.py` `existing_tree` branch.

*Directions to plan:*
- Make the canopy-height path work in an installed copy. Options: get rasterio
  into the builds (the reason it was dropped was a Rosetta CI Mac, and the Mac
  build now runs on `macos-15`, so retry it); or read the GeoTIFF window without
  GDAL (the tiles are Cloud-Optimised GeoTIFFs, and a ranged-read decoder in
  plain Python is possible, as `vector_tiles.py` is for map tiles); or ship
  pre-found treetops for the region (F277).
- Say honestly which source a scan used, and fix the "couldn't reach" message.
- In the review list, let the person correct each tree: conifer or broadleaf,
  height, and ideally a species from the region's list (*this is an aspen*). With
  a species, the 3D view can draw that species' read crown.
- Draw an unknown tree as neither conifer nor broadleaf: a neutral crown that
  says it is unknown, while the shade model keeps year-round shade.
- Give existing conifers and broadleaf trees a stand-in species' V3.50 crown
  (White Spruce, Trembling Aspen) instead of the generic tree.
- Note that Meta's canopy-height map is from imagery of about 2018–2020. A tree
  planted or felled since is outside what it can know. Say so in the review list.

*Questions:* was V3.67 installed or run from source? Which trees were wrong,
on which lot? Can the owner run a scan on the same lot and read the status line?

### F277 — The scan in seconds (item 2)

*Today:* buildings come from three public Overpass servers in turn, each given 30 s
(`osm_features._TIMEOUT`), with a pause and a retry when one is busy, and then
OpenFreeMap's vector tiles. **A bad minute is two to three minutes** before
anything comes back. The first tree scan also downloads Meta's whole tile index.
An offline **building pack** exists (`building_store.py`, `building_downloader.py`,
*Download buildings for this area* on Site › Features), and an Edmonton LiDAR
**contour** pack (`terrain_store.py`), but each has to be downloaded by hand, and
the tester did not know about either.

*Directions to plan:* ship the Edmonton region's buildings (OSM, ODbL: needs
attribution and share-alike for the extract, which `services.py` can carry), its
treetops (from the canopy-height map, CC BY 4.0) and its slope with the region
pack, so a scan inside the pack's circle reads from disk in under a second, and
only falls back to live search outside it. Measure first: the size of each layer
for the pack's 50 km circle, and how much installer size that adds. The decision
on installer size is the owner's.

*Questions:* is a bigger download acceptable (likely tens of MB)? Should the
data be in the installer, or fetched once on first use?

### F278 — Sun and shade as one path (items 3, 4)

*Today:* the Site tab reads *Site Info · Slope · Sun & Shade · Wind · Features ·
Notes*, so Features comes **after** the page that needs it. Sun & Shade opens on
*When* (date and the sun-time slider), then *Cast shade* (the existing-features
list, Opacity, Show shade), then the sun's arc, then planting zones
(`analysis_panel.py` ~L180–420). The slider sits above a shade map that does not
exist yet, so when shade is finally drawn it is out of sight above the button
just pressed. That is why it was missed. The sun path and the shade are drawn
separately and know nothing of each other. The guide (`data/guide.md`) never
mentions shade.

*Directions to plan:* put Features before Sun & Shade, or fold the scan into Sun &
Shade's first step. Order the page as steps: 1 what casts shade, 2 show shade,
3 move through the day. When shade is drawn, put the time scrubber on the map,
in a bar like the placement bar, with a play button that sweeps the day. Draw the
sun's position on the arc *at the slider's time*, so the arc explains the shadow
being shown. Perhaps add hours of sun per spot as a summary (planting zones
already classify it).

*Questions:* should Sun & Shade be in the simple app at all, or only its result
(planting zones, the plan reading shade)?

### F279 — Select everything, move everything (item 5)

*Today:* Ctrl+A and the marquee select plants, structures, shapes and
measurements (`04-tools.js` `selectAll`, `01-core.js` `_marqueeHitTest`), but a
drag moves **only the plants** in the selection (`03-plants.js` `_scopesFor` /
`onSelectionMoved`). A pond or brush pile is selected and stays put. Delete
already removes every kind in one undo step (`onSelectionDeleted`, V3.11), so the
pattern for moving them all exists.

*Directions to plan:* one `onSelectionMoved` carrying every kind, as one undo
step, with existing trees and buildings left out unless asked (they mark what is
really there).

### F280 — One way to put things on the map (items 12, 10, 17)

*Today:* two lists overlap. Structures (`db/structures.py`): Pond, Bioswale, Rain
Garden, Rain Barrel, Bee Log, Bee Hotel, Brush Pile, Snag, Rock Xeriscape, Native
Lawn Patch, Raised Bed, Compost Bin, Shed, Fence / Wall, Fire Pit. Shapes
(`shape_tool.AREA_PRESETS` and the lines): Garden Bed, Pathway, Patio / Deck, Lawn
Area, Mulch Area, Water Feature, Custom, Hedge, Fence, Living fence, Windbreak.
*Pond* and *Water Feature*, *Fence / Wall* and *Fence*, *Native Lawn Patch* and
*Lawn Area*, *Raised Bed* and *Garden Bed* are each one thing two ways. A
structure is a point with a fixed size. A raised bed is drawn on the map as a
3 × 1.2 m rectangle, but the 3D scene gets only its `size_m` (no width, no turn)
and draws a stock model (`scene_contract.py` structure branch, `05-flowers.js`
`buildStructures`). That is item 17.

Missing kinds the tester asked for: path surfaces (stone, mulch, gravel; there is
one *Pathway*), doors, downspouts and spouts, and **mulch around each plant**
(only *Mulch Area* as a drawn shape; `site_prep` already costs mulch for the
beds).

*Directions to plan:* one palette, grouped by what a thing is, where anything
with an outline is drawn (raised bed, pond, rain garden, patio) and anything that
is an object is placed (bee hotel, barrel, downspout, door). Each drawn kind has
its 3D look (`scene_site.SURFACE_KINDS`, which V3.45 made the one vocabulary), and
a raised bed is drawn in 3D at its outline and a height. Path surface becomes a
choice on Pathway. Doors and downspouts sit on a building's wall. Mulch rings
could be a per-plan option drawn by the 2D map and the 3D ground. Old designs
must keep opening, so this needs a file-format step and a test.

*Questions:* merging the lists moves things people know where to find. Is the
owner happy for Structures to become a group inside one palette?

### F281 — Water in the design (item 11)

*Today:* the generator puts water structures on low ground (`zoning.WET_STRUCTURE_IDS`)
and nothing else knows where water comes from. The app has no downspout anywhere
(the word is only in lesson text). And a **placed rain garden is a keep-out**
(`exclusion.EXCLUDING_STRUCTURE_IDS`), so Plan My Yard plants *around* a rain
garden and never in it, which is the opposite of what one is for. The Water page
(`water_budget.py`) counts barrels and ponds but does not place anything.

*Directions to plan:* downspouts as objects on a building's wall (F280). From
each, the ground's slope (already fetched for Slope) says where water runs, and
the plan suggests a rain garden or barrel there, says why, and plants the rain
garden with the region's plants that take wet feet and dry spells
(`zoning.needs_standing_water` is the 23 that need standing water, too strict).
An overlay could draw the runoff path.

*Questions:* should the app suggest placements (a note and a ghost) or place
them? Edmonton's rules on downspout disconnection and setbacks from foundations:
the owner may know which apply. The app should say, not guess.

### F282 — The bee game, refined (items 7, 18)

*Today:* *Fly as…* lists **681 animals** (338 bees, 189 moths, 154 butterflies),
in genus order, of which **475 have only a Latin name**
(`scene3d_creatures.rows`). The list is not filtered by `fauna_fit`, so animals
never recorded near the yard are offered (the Regal Fritillary, *Argynnis
idalia*). The window starts on a sensible animal (V3.44 `default_row`), but
choosing another means scrolling a wall of Latin. **58 of 1,144 animals have a
photograph.** The V3.55 fetch for the rest (`scripts/fetch_animal_photos.py`,
the owner's PC) has not been run. The walk's cards already do what the tester
asked for: an animal's photo, its plants here and not here, each a link
(`walk_cards.py`, `25-cards.js`). The bee game does not open them.

Item 18: the viewer takes no keyboard focus when *Fly as a bee* is pressed
(`scene3d_window` never calls `setFocus` on it), so the keys do nothing until a
click. The HUD's line is *"WASD fly · Q/E up-down · right-drag…"*. Nothing says
that the glowing orbs are flowers to fly into, until one is reached.

*Directions to plan:* a short picker of the region's well-known pollinators
first (recorded *here*, English-named, photographed: bumble bees, mason bees,
leafcutters, sweat bees, swallowtails, the Mourning Cloak, Painted Lady, Monarch,
fritillaries, sphinx moths), with *All animals…* behind them. Choosing one opens
its card (photo, a few lines, its plants), with *Fly as it* on the card. Run the
animal photo fetch. Focus the viewer when a mode starts. A first-time line:
*fly into the glowing flowers to drink*.

*Questions:* which ten or so animals should lead? The owner knows the region;
the records can rank by count near the yard as a first draft. The descriptions:
`fauna.description` is filled for all 1,144, but it needs reading for tone
before it is shown to beginners.

### F285 — Words a beginner can act on (items 14, 15, 16)

*Advanced tools (14):* the switch is **View → Advanced tools** and nowhere else
(`advanced_tools_flow.install`). The guide mentions it once. A beginner does not
open View. *Directions:* a visible switch at the side panel's foot or the
toolbar's end, saying what it adds.

*Edible (15):* the filter is `edible_parts IS NOT NULL AND != ''`
(`db/plants.py` ~L2982). **180 of 424 plants** carry something, and the parts
include "needles (tea)", "resin", "inner bark", "buds" (Balsam Poplar), "pollen",
"leaves?" and "seeds?". *Directions:* a narrower filter, *Fruit or nuts you would
pick* (fruit, berries, nuts, seeds where clearly food), with the full list under
the plant page's Good to know. **P12:** many of the obscure entries are
plant-use traditions, likely Indigenous in origin, and come from ethnobotanical
sources. Narrowing what the filter promotes is in the spirit of P12. This
section must **not** add, expand or reword use records. Any rewording of
`edible_parts` itself stops for the owner.

*Food for a fussy eater (16):* the toggle's words are `plant_filters.py` L162.
The explanation is only in a tooltip, which a tester never sees. *Directions:*
words that say it, e.g. *Feeds an animal that eats only a few plants*, or a short
line under the toggle; the word list in `docs/homeowner/09-words.md` gets the
change.

### F286 — The first launch says it is working (item 9)

*Today:* `main.py` → `app._init_database` runs `init_db()` on the main thread
before any window. A fresh database takes 1.3 s in this container (measured; a
Windows laptop with antivirus scanning a new 20 MB file can be several times that).
After it come QtWebEngine's first start (Chromium) and the start screen. Windows
shows *(Not Responding)* after about 5 s without the message loop running.
**Not measured:** where the time goes on a Windows machine; no session has one.

*Directions to plan:* measure first, on the owner's PC (a timed launch log with
a line per stage). Then a splash or the start screen shown at once, with the
database and the web engine started behind it, so the message loop never stops
for long.

*Question:* was this the very first launch after installing or updating (the
reseed), or every launch?

### F287 — The PDF report in colour, and adding up (items 6, 19–21)

*Answered (second message):* the tester ran **V3.67**, and "the report card"
meant **the PDF's first page**, *How your yard is doing*, which
`pdf_export._draw_overview` draws from the same items as Design › Overview. So
the retired Report card is not missed. Their verdict on the report: "nice". Three
things would make it better.

*Status words all green (item 20).* On screen each status word has its own colour
(`yard_overview_page._STATUS`: green for *Looks good*, amber for *Worth a
look*, grey-blue for *To plan for*). The PDF writes the word into the item's
title line in the heading colour (`HEAD`, dark green), so all three look the
same. *Direction:* draw the word in its own colour, one colour per status, each
dark enough for 4.5:1 on white paper. The PDF needs darker shades than the
screen's, which is dark. Keep the word itself (§4 rule 7: never a colour
alone). Check how it prints in greyscale.

*Plant colours (item 19).* The tester: "The plants colour can be changed manually
but there ought to be an option to have each species show a different colour
with a legend, or even have the type colour for the plants show." What the code
does:
- **On screen**, plants are already coloured by type (`member_colors.TYPE_COLORS`,
  mirrored in `10-plant-key.js`), or by the colour a person gave them. The
  legend (View, `12-legend.js`) lists them by *Type* or *Species*, but in
  Species mode every species keeps its type's colour, so twelve wildflowers are
  twelve purples, told apart only by number.
- **In the PDF**, the planting map (`pdf_export._draw_planting_map`) fills every
  plant with the same pale green (`#dcedc8`) and a number. It ignores both the
  type colours and any colour picked by hand.

*Directions:* the PDF map in the type colours by default, keyed by type beside
the numbered key, with the person's own colours honoured. Then an option, on
screen and in the PDF, to colour **by species**. One honest limit: past about
ten or twelve, colours stop being told apart (V2.69 measured the same thing for
ecoregions), so a species palette should give the most numerous species their
own colours, keep the numbers for all, and say so. Where the choice lives (the
legend's Type/Species switch already exists on screen) is for the section's plan.

*Total cost (item 21).* The plain-text planting plan
(`planting_plan.format_plan`) already ends with plants, structures, mulch and an
*ESTIMATED TOTAL*. The PDF's *What to buy* page (`pdf_export._draw_planting_plan`)
lists each line's range and **never adds them up**. *Direction:* a subtotal per
source and the same total lines the text export has, from the same
`PlantingPlan` fields (`grand_low` / `grand_high`), so the two cannot disagree.
Say it is a range and where the prices come from (`price_words`), as the text
export does.
